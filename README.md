# Court Semantic Search

Поиск судебных актов по описанию ситуации. Сначала интерфейс показывает
предварительные интернет-находки со ссылками (если подключён Yandex Search API), затем
поисковые формулировки и обязательные признаки от GigaChat. Каждую строку можно
исправить и подтвердить галочкой «ОК». Поиск начинается только по отдельной кнопке
после согласования; изменение текста требует повторного подтверждения.

Parser API возвращает кандидатов. До загрузки PDF приоритет определяется словами
в формулировках, по которым источник вернул акт. Для прочитанных PDF вычисляется
реальное количество различных слов из согласованных формулировок с учётом
словоформ во всём тексте. Этот порядок предшествует смысловой проверке.

При включённой смысловой проверке GigaChat отвечает на вопросы о каждом
обязательном факте по **всему извлечённому тексту выбранного акта**, связывая
участников и события между страницами. Для длинных текстов читаются все части,
затем сопоставляются факты в общем списке с названиями компаний и цитатами.
Подтверждение может содержать несколько цитат из разных частей. Цитаты
проверяются дословно. Без завершённого анализа подтверждённая подборка не
пополняется. Результаты и объяснения нужно сверять с оригиналом судебного акта.

Оценки дел, качества PDF и рассмотрения вопроса по существу сохраняются в браузере
и экспортируются в JSON. Числовые оценки плана и его признаков заменены
редактированием и галочками.

## Запуск

Нужен Python 3.10+; выполните команды из корня этой копии проекта.
Создайте `.env` из `.env.example`, заполните `PARSER_API_KEY` и
`GIGACHAT_AUTH_KEY` (готовый ключ авторизации из личного кабинета GigaChat API).
Ключи не надо передавать в чат или команды запуска. Если `.env` уже есть,
замените `LLM_PROVIDER` на `gigachat` и добавьте `GIGACHAT_AUTH_KEY`.

macOS / Linux:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
.venv/bin/python -m backend.scripts.audit_startup
.venv/bin/python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
.\.venv\Scripts\python.exe -m backend.scripts.audit_startup
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Откройте `http://127.0.0.1:8000/demo`. На странице виден идентификатор версии
запущенного процесса. После обновления Python-кода или `.env` перезапустите сервер.
`.env` читается только из корня исполняемой копии; переменные окружения имеют
приоритет. Соседние `.env` не загружаются. `/api/demo/status` проверяет наличие
настроек, а не действительность ключей или доступность сети.

Реальный режим: `COURT_PROVIDER=parser_api`, `LLM_PROVIDER=gigachat`,
`GIGACHAT_PLAN_MODEL=GigaChat-2`. Для смысловой проверки при отдельном согласии
по умолчанию выбрана `GigaChat-2-Pro`; модель можно изменить через
`GIGACHAT_RELEVANCE_MODEL`. `GIGACHAT_SCOPE` должен соответствовать вашему типу
доступа: `GIGACHAT_API_PERS`, `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP`.
Режим `COURT_PROVIDER=mock` использует учебные PDF. Yandex Search API отвечает
только за предварительный интернет-поиск; план и анализ PDF используют GigaChat.
`YANDEX_API_KEY` можно повторно использовать для интернет-поиска при наличии
нужной роли и области действия. Настройки прежнего YandexGPT-планировщика
не переключают основной `LLM_PROVIDER` с GigaChat.
Проверка TLS включена. На этом Mac системное хранилище не доверяло цепочке
`Russian Trusted Root CA` для GigaChat. В `certs/` лежит публичный корневой
сертификат из URL, указанного в
[официальной инструкции Сбера](https://developers.sber.ru/docs/ru/gigachat/certificates),
с проверенным SHA-256-отпечатком; он применяется только к HTTPS-вызовам
GigaChat при указании `GIGACHAT_CA_BUNDLE` в серверном `.env`. Системное хранилище
macOS не изменено, проверка TLS не отключена. Parser API с включённым VPN
по-прежнему может не завершать TLS; проверяйте его в рабочей сети сервиса.

## Ограничения поиска

| Этап | По умолчанию |
|---|---|
| Построение плана | 45 секунд |
| Весь evidence-поиск | 300 секунд |
| Поиск кандидатов внутри этого бюджета | до 45 секунд |
| Одна операция Parser, включая все попытки | 25 секунд, 1 попытка |
| Объём в обычном режиме | до 3 формулировок × 1 страница и до 2 PDF: до 5 операций Parser API |
| Объём в расширенном режиме | формулировки плана, до 2 страниц на формулировку; до 10 поисков страниц/историй и 6 PDF за порцию |
| Извлечение одного PDF | 15 секунд; до 10 MiB, 200 страниц, 500000 символов |
| Смысловая проверка полного текста | до 180 секунд на этап; весь текст выбранных актов, несколько вызовов для длинных решений |
| Предварительный интернет-поиск | до 30 секунд; Yandex Search API с генеративным ответом |

Пользовательские `max_pages_per_query`, `max_search_calls` и `max_cases` не обходят серверные
ограничения. Любое усечение, сбой источника или непроверенный PDF явно отмечается
в `partial`/`warnings`. `cases_checked` означает успешно прочитанные PDF;
`cases_attempted` — дела, для которых начата попытка чтения PDF. Процессуальные
акты не занимают PDF-слоты, если доступны другие кандидаты. Если источник отвечает медленно, часть
формулировок не успеет выполниться, и ответ будет помечен как неполный.
`diagnostics` содержит реальные числа
операций, HTTP-попыток, успешных ответов Parser API, загрузок, байтов и длительности.
Каждая выполненная формулировка вызывает отдельный `/search`, а каждый проверяемый
не сохранённый ранее PDF — отдельный `/pdf_download`. Новый запуск снова ищет
кандидатов; текст успешно прочитанного PDF может быть использован из кэша.
По [документации Parser API](https://parser-api.com/ras-arbitr-ru)
лимит расходуют ответы `done=1`; число HTTP-попыток может быть выше числа
успешных ответов. План GigaChat не расходует лимит Parser API.

Категории не исключаются глобально. Только при запросе налогового предмета без
запроса банкротства акты, все метаданные которых прямо указывают банкротство или
реестр кредиторов, пропускаются до загрузки PDF. Участие ИФНС и ссылка на НК РФ
сами по себе не подтверждают налоговый предмет. Явные ограничения
передаются через `filters`; даты проверяются после ответа источника. Указанные
пользователем исключения сохраняются в плане, а их словесные упоминания в PDF
показываются отдельно для проверки контекста. Одна совпавшая формулировка не
равна одному подтверждённому факту.

Выбор формулировок учитывает обязательные условия и не отдаёт преимущество
одной ссылке на норму. Сначала загружается первая страница каждой формулировки,
затем следующие страницы в пределах общего лимита операций. `query_progress`
показывает число страниц источника и точные номера полученных страниц по запросу.
Если у дела не найден акт по существу, `max_case_expansions` разрешает запросить
первую страницу документов по его номеру. Чужие идентификаторы дел отбрасываются;
полнота истории и последняя инстанция этим не гарантируются.

Выбор PDF отдаёт приоритет кандидатам с большим охватом слов согласованных формулировок по выдаче источника.
Процессуальные определения не вытесняют решения по существу; определения,
разрешающие самостоятельный вопрос, не запрещены по названию. Без данных о
назначении определения его статус остаётся неизвестным.

`recommendation_status` отделяет `confirmed` (высокое сходство и все условия
подтверждены моделью дословными цитатами), `related` (частичное сходство при
подтверждённых условиях), `unverified` (недостаточно подтверждений) и
`not_recommended` (низкое сходство, процессуальный акт или показанное несоответствие).
Подтверждение относится к проанализированному акту и требует проверки оригинала.
Высокая оценка без цитаты хотя бы по одному обязательному условию не допускает
дело в подтверждённую подборку. Словесная оценка никогда не подтверждает
юридическое сходство. Интерфейс группирует результаты по этим статусам, затем
сортирует по `relevance_score`. `relevance_status` различает `semantic`, `textual`,
`insufficient` и `unverified`.
Сортировка не гарантирует, что нужное дело было в первых страницах источника
или в шести PDF. `semantic_reranking` по умолчанию выключен: значение `true`
означает разрешение передать GigaChat описание, обязательные признаки и полный извлечённый
текст выбранных актов. `not_shown` означает, что модель не нашла подтверждения в
прочитанном материале, а не доказала отсутствие события.

### Обновление по отзывам 29 сентября

Инструкции модели сохраняют объект сделки, направление присоединения,
переход обязанности и альтернативы, а также отличают предмет спора от
участия ИФНС. Посторонний английский текст в сгенерированном русском плане
отклоняется до поиска. Подтверждающие и опровергающие цитаты проверяются
дословно; отсутствие факта во фрагментах не приравнивается к его опровержению.

Экспорт оценок версии 2 содержит `runs` (объект по ID запуска) и `entries`
с полем `run_id`. Каждый запуск хранится один раз, включая `result_snapshot`:
число кандидатов, все возвращённые карточки, оценки, цитаты, ошибки PDF,
предупреждения и диагностику. Старые оценки версии 1 в браузере сохраняются
при миграции. Файл оценок можно импортировать обратно. Открытие PDF, рассмотрение вопроса по существу и релевантность
дела оцениваются отдельно.

Для повторного тестирования выберите расширенный режим и явно разрешите
смысловую проверку. В существующем `.env` установите
`SEARCH_MAX_PAGES_PER_QUERY=2` и `SEARCH_MAX_SEARCH_CALLS=10`, если прежние
значения ограничивают глубину; затем перезапустите сервер. Экономный режим
сохраняет предел 3 поисков и 2 PDF. Все изменения проверяются тестами без
внешних вызовов; качество живой выдачи подтверждается отдельным тестом юристов.

### Обновление по отзывам 1 октября

`coverage_mode="full"` включает последовательный обход **всех** формулировок
плана по периодам. Период задаётся фильтрами; без них используется 1900-01-01
по дату начала поиска. Если выдача велика или `count` больше доступных страниц,
период делится на непересекающиеся половины. Старшая по давности половина
обрабатывается первой, страницы небольших периодов дочитываются. Лимиты времени
и операций действуют **на порцию**, а не отключаются. `continuation_token`
позволяет продолжить с очередной страницы/периода, сохранив кандидатов. Передавайте
тот же `description`, `plan`, фильтры, `reference_case_number` и режим смысловой
проверки. Ошибочная страница сохраняется для следующей порции. Ограничение даже
одного дня, повтор страницы или несогласованное число документов блокируют
подтверждение полноты; `retrieval_complete` остаётся false.

Токен — случайный идентификатор серверной сессии. Сессии и тексты PDF хранятся
в памяти процесса: до часа простоя, максимум 32 сессии по 20000 документов и
5 млн символов текста суммарно. Перезапуск, истечение срока или вытеснение
истории требуют нового запуска. Для нескольких процессов нужен общий backend
хранения или привязка запросов к одному worker. Текущий MVP запускать с одним
worker. Полный обход выдачи по выбранным словам не гарантирует полноту корпуса
источника или обнаружение всех юридически близких дел. Документация Parser не
определяет сортировку и логику сочетания слов; приложение их не выдаёт за
проверенные AND/OR или точную фразу.

В режиме продолжения уже прочитанный акт не занимает PDF-слот повторно; если
получен другой акт по существу того же дела, он может быть проверен. Неудачная
загрузка остаётся доступной для повторной попытки. Успешно извлечённый текст
кэшируется отдельно от оценок: повторное сравнение не загружает этот PDF и не
использует устаревший юридический вердикт. `pdf_cache_hits` показывает чтения
сохранённого текста; `pdf_calls` — новые запросы PDF к источнику.

`excluded_case_ids` позволяет передать отклонённые дела до расширения истории и
PDF-проверки. Интерфейс использует **только оценки kind=case 1/2**, последнее
решение по идентификатору, для того же нормализованного описания. Высокая оценка
качества PDF или акта не означает релевантность дела. Это учёт отзывов, а не
автоматическое обучение модели; для другого запроса дело не исключается.
Настройку можно отключить. `feedback_cases_skipped` показывает число пропусков.

`reference_case_number` добавляет образец по отдельному поиску номера без текста
и ограничений основного запроса. Один поисковый слот первой порции резервируется
для него. `is_reference` отличает такой образец от естественной выдачи. Указанный
юристом А68-10855/2018 принят как контрольный реквизит; дата 28.12.2024 и содержание
требуют сверки с первичным актом. Тесты используют синтетические данные, не текст
этого решения. Подстановка образца не считается успешным поиском по описанию.

Счётчики в интерфейсе разделяют кандидатов, новые операции, проверки сохранённых
PDF, исключения и смысловой режим. `parser_successes` означает полученный
`done=1`; последующая обработка может отклонить его данные. Остаток подписки
по этим числам не определяется. `stage_seconds` суммирует длительности операций,
поэтому параллельные PDF могут дать сумму больше `total_seconds`. События
`parser_http` и этапа описывают одну операцию, а не два списания.

Планировщик получает исправления ролей и направления действий из отзывов,
сохраняет альтернативу займа/кредита и долга/убытков, не превращает расходы в
вычет и не фиксирует исход спора. Пропущенный явно заданный налоговый предмет
добавляется в критерии, обнаруженная перестановка заемщика отклоняется до
обращения к источнику. GigaChat один раз исправляет некорректный план в пределах
общего времени планирования. В словесной проверке `долг/убытки по займу` сохраняет
общую связь с займом в обеих ветвях. Смысловая проверка остаётся по явному согласию.

### Обновление 2 октября: согласование, вопросы о фактах, полный текст

Два поисковых POST-метода требуют `plan` и `plan_approval` с точными списками
`queries`/`must_have` текущего плана. Без согласования сервер возвращает 409;
устаревшее подтверждение после редактирования — 422, без обращения к источнику.
Каждая строка подтверждается отдельно в интерфейсе. По умолчанию выбран режим
по периодам, чтобы постепенно выполнять все согласованные формулировки.
Продолжение передаёт тот же согласованный план. Для собственных API-клиентов
подтверждение необходимо добавить явно.

Словесный этап использует только поисковые формулировки, а обязательные признаки
задаются модели как вопросы о фактах. `lexical_word_count`, `lexical_total_words`
и `lexical_matched_words` показывают совпадения в полном прочитанном тексте.
До загрузки PDF словесная оценка по выдаче источника остаётся приблизительной;
бюджет загрузок не позволяет утверждать, что непрочитанные кандидаты содержат
меньше слов. Итоговые результаты группируются по подтверждению условий и
сходству; словесная сортировка служит предварительным этапом.

`analysis_complete` и `analysis_scope` показывают завершённость анализа акта.
Короткий акт передаётся целиком. Длинный акт разбивается на последовательные
перекрывающиеся части, **каждая** читается моделью; затем общий список фактов
сопоставляет имена, роли, события и даты. Никакого отбора пяти «наиболее
подходящих» выдержек для этой проверки нет. `semantic_criteria[].reason` содержит
ответ и объяснение; `citations[]` — все его основания из разных частей текста.
Если хотя бы одна обязательная подтверждающая цитата выдумана, положительный
ответ заменяется на `unclear`. Старые поля `quote`/`highlights` сохраняют первую
цитату для совместимости.

При таймауте, незавершённом извлечении фактов или слишком большом итоговом списке
для контекста акт остаётся непроверенным, а в режиме продолжения доступен
повторно. Уже завершённые оценки других актов сохраняются. Лимиты PDF (размер,
страницы, извлечённый текст) отклоняют слишком большой документ с ошибкой,
**не обрезают** его и не подтверждают условия по началу. OCR пока нет: полный
текст означает весь текст, который удалось извлечь из выбранного PDF, а не
содержимое сканированных страниц или полную историю дела.

Для интернет-поиска задайте `YANDEX_SEARCH_API_KEY` и `YANDEX_FOLDER_ID`
в серверном `.env`. Если отдельный поисковый ключ пуст, используется существующий
`YANDEX_API_KEY`. Сервисному аккаунту нужна роль `search-api.webSearch.user`
на каталог, а API-ключу — область `yc.search-api.execute`; ключ только для
YandexGPT может не иметь этих прав. Настройка описана в
[инструкции Яндекса](https://aistudio.yandex.ru/ru/docs/search-api/operations/generative-search).
Search API тарифицируется отдельно: проверьте платёжный аккаунт и
[тариф](https://aistudio.yandex.ru/ru/docs/search-api/pricing).

Ключ остаётся на сервере. Используется официальный
[REST API генеративного поиска](https://aistudio.yandex.ru/ru/docs/search-api/api-ref/GenSearch/search),
русский поиск по всему индексу без ограничения заранее выбранными сайтами.
Сводка отображается вместе с источниками, отмеченными Яндексом как `used=true`.
Номера ссылок сохраняют позиции в исходном списке. Если сводки нет, она отклонена
или не имеет используемых источников, показываются только найденные страницы.
Кликабельные ссылки берутся из метаданных поиска и допускают только HTTP/HTTPS
без учётных данных. Текст ответа отображается как текст; HTML от модели не исполняется.
Обращения к Gemini/Google удалены, автоматического перехода к ним нет.

Интернет-находки не подтверждают судебные факты автоматически и не меняют план
без согласования. Не подключённый сервис, отсутствие находок, таймаут и ошибка
доступа отображаются явно. Ошибка интернет-этапа позволяет составить основной
план. Повторные платные запросы автоматически не выполняются; при превышении
квоты пользователь получает сообщение о лимите.

Зависимость от доступа к Google убрана. Работу всего сервиса без VPN нужно
проверить в сети его размещения: Yandex Search API, GigaChat и Parser API должны
быть доступны с сервера. `backend.scripts.audit_startup --network` проверяет
HTTPS без ключей и расхода поисковой квоты; успешное соединение не подтверждает
права ключа, баланс или доступность всех ссылок, найденных в интернете.

Если локальный `.env` закреплял прежние таймауты, для длинных актов установите
`SEARCH_TIMEOUT_SECONDS=300` и `RELEVANCE_TIMEOUT_SECONDS=180`. После обновления
перезапустите сервер. Настройки и ключи в текущем `.env` автоматически не меняются.

## Проверки

Обычные тесты не расходуют внешнюю квоту:

```sh
python -m pytest -q
```

Диагностика запуска и HTTPS без отправки ключей в сетевые пробы:

```sh
python -m backend.scripts.audit_startup --network --output startup-audit.json
```

Интеграционный smoke с реальным Parser API (до 2 поисков и 1 PDF):

```sh
python -m backend.scripts.smoke_parser --output parser-smoke.json
python -m backend.scripts.smoke_parser --with-gigachat --output full-smoke.json
```

Вторая команда дополнительно делает один вызов GigaChat, который может тарифицироваться. Не нужно запускать
обе команды для одной проверки. Exit code 0 означает, что все обязательные этапы
прошли; exit code 1 — проверка не пройдена. Нет подмены Parser на mock.

Отдельно проверить только GigaChat, не обращаясь к Parser и PDF, можно одной
явно запущенной командой (один вызов модели, возможна тарификация):

```sh
python -m backend.scripts.smoke_gigachat --output gigachat-smoke.json
```

26 сентября 2026 года с локальным ключом проверены реальные вызовы GigaChat:
план на `GigaChat-2` сформирован за 1,54 с; `GigaChat-2-Pro` на двух вымышленных
фрагментах дал оценки 5 для совпадающего спора и 0 для другого предмета.
`/api/demo/status` после запуска показывает `ready=true`. Parser API и реальные
судебные PDF в этом запуске не проверялись из-за сетевого маршрута с VPN.

Можно включить live pytest отдельно: `RUN_PARSER_API_SMOKE=1 python -m pytest -m integration -q`.
В PowerShell сначала `$env:RUN_PARSER_API_SMOKE="1"`, затем запустите pytest.

Если TCP работает, а `start_tls` завершается таймаутом, проверьте сетевой маршрут
к Parser API. Это не доказательство неверного ключа. Не отключайте проверку
сертификатов: обе интеграции используют системное хранилище. Во время аудита
25 сентября Parser не завершил TLS при включённом VPN; успешная реальная
PDF-загрузка в том запуске не подтверждена. Для GigaChat без VPN/ключа живой
вызов отдельно не подтверждён.

Если GigaChat возвращает HTTP 401/403, проверьте ключ авторизации и `GIGACHAT_SCOPE`
в личном кабинете. Ключ обновляйте только в локальном `.env`, не отправляйте в чат.

## API и данные

- `POST /api/cases/web-preview` — предварительный интернет-поиск, без вызова Parser.
- `POST /api/cases/plan` — план без вызова Parser.
- `POST /api/cases/search-with-evidence` — ограниченный поиск, PDF и цитаты.
- `POST /api/cases/semantic-search` — кандидаты без PDF, с диагностикой.
- `GET /api/cases/search` — структурированный поиск и ограниченное расширение истории дела.
- `GET /api/documents/search` и `POST /api/documents/extract-text` — операции с актами.
- `POST /api/cases/extract-factual-base-text` и `extract-latest-substantive-text` — явные роли документов.
- `POST /api/cases/extract-preferred-text` — совместимость со старым API.
- `GET /api/collections/search` — подборки по фильтрам.

```json
{
  "description": "Налоговый орган исключил расходы по договору займа как экономически необоснованные.",
  "max_pages_per_query": 1,
  "max_cases": 6,
  "semantic_reranking": true,
  "plan": {
    "queries": ["проценты по займу", "расходы заем деловая цель"],
    "must_have": ["Налоговый орган оспаривает расходы по займу"],
    "filters": {"dateFrom": "2020-01-01", "dateTo": "2025-12-31"}
  },
  "plan_approval": {
    "queries": ["проценты по займу", "расходы заем деловая цель"],
    "must_have": ["Налоговый орган оспаривает расходы по займу"]
  }
}
```

В evidence-поиске выбирается фактическая база из уже найденных актов; полная
история каждого дела автоматически не скачивается. `evidence_document` — именно
документ, откуда взята цитата, с CaseId, document_id, датой, судом и FileUrl.
Ключи, исходные PDF и пользовательские поиски в БД не сохраняются.
