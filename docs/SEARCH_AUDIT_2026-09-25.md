## Итог и границы проверки

Обнаружены независимые причины задержек и искажений выдачи. Исправлены ограничения времени и объёма, смешение метрик, тематические исключения, выбор источника цитаты, загрузка конфигурации и сбор оценок. Полноценная семантическая проверка юридических фактов остаётся отдельным этапом roadmap; словесное совпадение больше не выдаётся за её результат.

Реальный Parser API в текущей сети не прошёл TLS-рукопожатие. DNS и TCP работают, но HTTP-ответ не получен. VPN включён; сравнение без VPN не выполнялось, поскольку пользователь сообщил, что это прервёт работу Codex. Поэтому влияние VPN — гипотеза, а валидность ключа Parser API, результаты поиска, реальные PDF и качество выдачи **не подтверждены**. TLS-проверка сертификатов сохранена.

## Что проверено до изменения алгоритма

- Работают две разные копии репозитория: проектный mirror со старым HEAD `8f63eb5` и используемая пользователем рабочая копия с HEAD `e62509a`. Процесс на порту 8000 запущен из рабочей копии. Исправления предназначены для неё; ранее незакоммиченные изменения сохранены и переработаны в рамках этой задачи.
- `/demo` реально отдавал вызов `/search-with-evidence`, `max_pages_per_query: 3`, `max_cases: 12`. Эта задержка не объясняется одним кэшем браузера.
- Все три настройки доступа (Parser key, Yandex key, Yandex folder) присутствуют. Значения не выводились. Наличие ключа не доказывает авторизацию.
- Yandex действительно сформировал план за 1,87 с. После изменения контракта плана повторный smoke подтвердил Yandex за 2,532 с. Выявлен и исправлен ответ 400: Yandex требует все свойства JSON Schema в `required`; необязательные фильтры передаются как nullable-поля.
- Parser: поиск по тексту завершился `ConnectTimeout` за 20,02 с; поиск по номеру дела — за 40,10 с. Это не ответ 401/403 и не установленная ошибка ключа.
- TCP до обоих сервисов установился примерно за 0,01 с. Trace HTTPS Parser: `connect_tcp.complete` → `start_tls.started` → `start_tls.failed`. И системные, и стандартные сертификаты дали `ConnectTimeout` примерно за 8 с.
- Старый набор: 33 зелёных теста; реальные внешние API не проверялись. Часть тестов закрепляла навязывание исключений банкротства.

## Причины в коде

| Участок | До аудита | Исправление |
|---|---|---|
| Конфигурация | `.env` и `../.env` зависели от текущего каталога; соседний файл мог перекрывать настройки | Один `.env` у корня исполняемого проекта; переменные окружения имеют обычный приоритет |
| План | Безусловные исключения банкротства в prompt и Python, плюс удаление исключений по слову в описании | Нет предметных запретов или исправления смысла плана эвристикой; исключения только из явного запроса |
| Сетевой объём | До 5 × 3 поисков + 12 PDF = 27 операций, до 81 HTTP-попытки | По умолчанию до 3 × 1 поисков + 3 PDF = 6 операций, по одной попытке |
| Тайминги | 120 с на ожидание сети, 3 попытки, нет общего серверного бюджета; браузер сдавался через 180 с | 25 с на всю операцию с повторами, 45 с на retrieval, 90 с на весь evidence-поиск; план отдельно до 45 с |
| Худший сценарий | Даже оценка 27 × (3 × 120 + 1 + 2) ≈ 9801 с не является строгой верхней границей, потому что HTTPX timeout не равен общему deadline | Последующие операции прекращаются при истечении бюджета; частичный результат явно помечен |
| Ранжирование | Большое число актов повышало позицию дела; первые четыре буквы считались совпадением; порог 75% скрывал результаты | Сначала число формулировок, затем морфологические словесные признаки в близком фрагменте; статусы и пропуски открыты |
| Даты | Семантический путь отправлял только text/page | Структурированные фильтры проходят к Parser; даты перепроверяются локально |
| PDF | Проверка одного preferred-документа, счётчик увеличивался до успешного чтения | Приоритет фактической базы, явный evidence_document, отдельные attempted/downloaded/checked |
| CPU PDF | Синхронное извлечение блокировало обработку других запросов | Отдельный завершаемый процесс; 10 MiB, 200 страниц, 500000 символов; большие/сканированные PDF явно непроверены |
| Ошибки | Некоторые ошибки авторизации превращались в общую 502; ошибка PDF попадала в число «релевантных» | Сохраняются классы и error_code; непроверенные PDF не подтверждают признаки |
| Логи | HTTPX мог выводить URL с ключом Parser | Ключ маскируется; диагностика содержит этапы, длительность, коды и счётчики |
| UI | Не было оценок; разные счётчики назывались совпадениями; старые карточки оставались при новом плане | Оценки формулировки/признака/дела/акта, локальное сохранение и JSON-выгрузка; ясные метрики; очищение старой выдачи |
| Версия | Сложно понять, какой код запущен | Отпечаток исходников при старте; `/demo` отдаётся с `no-store` |

Это консервативный профиль, а не обещание полной выдачи. Поисковый endpoint не расширяет каждое дело дополнительными сетевыми запросами. Полная история по `CaseId` остаётся в отдельном `/api/cases/search`.

## Замечания коллег, восстановленные по сообщениям и фотографиям

1. Безвозмездная передача созданного имущества государству: сохранять предмет налогового спора и указанные нормы; не подменять ситуацию займом или общими словами о расходах.
2. Приобретение компании с привлечением займа и последующее присоединение: сохранять роли приобретателя, целевой компании и заёмщика; не додумывать факт погашения долга.
3. Аренда с последующим выкупом: сохранять различие расходов на аренду и выкупной стоимости; налоговый спор не равен любому упоминанию НК РФ.
4. Систематическое преобладание банкротства требует анализа выдачи, а не глобального запрета этой категории. Нужен отдельный положительный сценарий банкротства.
5. «Одна формулировка нашла дело» не означает «совпал один юридический факт». Метрики разделены.
6. Нужны оценки каждой формулировки и судебного акта. Они добавлены, вместе с оценкой признака/дела и комментариями.
7. Цитата, ID документа и ссылка должны относиться к одному проверенному акту; суд и дата видны в карточке.

## Реальный интеграционный smoke

Команда `python -m backend.scripts.smoke_parser --with-yandex --output parser-smoke.json` проверяет реальные Yandex → endpoint → Parser search → PDF → извлечение и идентичность источника. Без `--with-yandex` используется фиксированный план, чтобы проверка Parser не зависела от LLM. Фейков и fallback на mock нет. Допустимы максимум два поиска и один PDF. Ошибка любого обязательного этапа даёт exit code 1.

Проверенный запуск с VPN: Yandex PASS; evidence endpoint ответил через **45,003 с** с `partial=true`; 2 поисковые операции / 2 HTTP-попытки, 0 PDF; полный smoke **FAIL**, поскольку источник не доступен по HTTPS. Общая длительность с планом — **47,538 с**. Сохранён [безопасный JSON-отчёт](audit/parser-smoke-vpn-2026-09-25.json). Пустая выдача в этом случае не интерпретируется как отсутствие судебной практики.

Результат без VPN следует сравнить теми же командами; не менять prompt, категории и пороги для компенсации сетевого сбоя. Не отключать TLS-проверку.

## Что ещё нельзя утверждать

- Лексические совпадения не проверяют роль стороны, отрицание факта, цитирование другого дела или итог решения. До внедрения/оценки семантического reranking UI говорит о словах признаков, а не процентах юридической релевантности.
- Три PDF — ограниченный shortlist, не все найденные дела. Неизвлекаемый текст требует OCR, который сейчас не реализован.
- Действительность Parser-ключа и успешность реальных PDF-загрузок надо подтвердить зелёным smoke в доступной сети. Нельзя заменить эту проверку зелёными mock-тестами.
- KAD, полнота процессуальной истории, изменения законодательства и судебных подходов остаются этапами исходного roadmap; этот аудит их не объявляет реализованными.
- Оценки сохраняются локально в браузере и экспортируются пользователем. Автоматического обучения на оценках нет.

## Основания контракта

- [Официальная документация Parser API](https://parser-api.com/ras-arbitr-ru): поддерживаемые фильтры, `done`, ошибки доступа, base64 PDF.
- [PyMuPDF multiprocessing](https://pymupdf.readthedocs.io/en/latest/recipes-multiprocessing.html): использование потоков для PyMuPDF не поддерживается, поэтому извлечение изолировано процессом.


## Локальная проверка изменений

Автоматические проверки включают тайм-ауты и отмену, ограничения числа операций,
сохранение кодов авторизации, фильтры дат, отсутствие тематического запрета,
морфологию/номера норм/близость слов, CaseId и точный документ цитаты, отсутствие
ключей в логах, изоляцию одновременных запросов и завершение PDF-процесса.
Live-тест по умолчанию пропущен, пока явно не включён.

В отдельной тестовой вкладке проверены учебный поиск, три карточки с цитатами,
оценки формулировки и акта, сохранение комментария, скачивание JSON и ссылка
именно на проверенный PDF. Ошибок выполнения JavaScript не обнаружено.
Проверка интерфейса с mock-данными не является проверкой качества реальной выдачи.

При финальной проверке конфигурации обнаружено, что рабочий `.env` явно
переопределял тайм-аут/попытки значениями 120/3. Они заменены на 25/1;
значения ключей не изменялись. Изменить только defaults в Python было бы недостаточно.


Проверка на момент первого аудита в рабочей копии: **57 passed, 1 skipped**; `git diff --check`
без замечаний. Пропущенный тест — отдельно включаемый live Parser smoke; его

## Дополнение: ошибочный фильтр из плана Yandex

В повторном запуске пользователя план Yandex сформировался за 1,973 с, но
Parser API ответил HTTP 400 (`40001`) за 2,582 с. На экране виден фильтр
`disputeType: reorganization_tax_benefit`, которого нет среди восьми допустимых
русскоязычных значений в документации Parser API. Модель добавила и дату
`2020-01-01`, хотя год в описании ситуации отсутствовал. Два независимых
сужения попадали из свободного ответа LLM в запрос к источнику без проверки.

Добавлена проверка на границе плана и Parser API. Сгенерированные поля
`case_number`, `inn`, `court` сохраняются, только если их значение есть в
описании; даты — только при явно названном периоде поиска; `dispute_type` —
только при точном документированном названии; `dispute_category` — только при
явно указанном номере категории. Остальные значения удаляются из плана до
поиска, не меняя формулировки и не исключая целые темы. Структурированные
фильтры, явно переданные API-клиентом, проверяются моделью запроса: неверный
вид спора или синтаксис категории получают 422 до обращения к Parser API.

После исправления локально пройден **61 тест**, один live-тест пропущен по
умолчанию. Повторный live smoke через текущую сеть: Yandex PASS за 2,85 с;
оба запроса Parser API ограничены общими 45 с и завершились тайм-аутом без
HTTP-ответа; PDF не загружен, полный smoke FAIL. Это не подтверждает качество
реальной выдачи и не повторяет исходный HTTP 400. Отдельная проверка Parser
и PDF остаётся необходимой в сети, где сервис стабильно отвечает.

## Дополнение: порядок выдачи и содержимое PDF

После двух пользовательских оценок 1/5 проверена вся цепочка ранжирования.
Ранее первые три дела выбирались по числу попаданий поисковых формулировок и
порядку Parser API; слова признаков искались по всему PDF. Это позволяло акту
о банкротстве и продаже дома получить частичные совпадения по «договору
поставки» (поставка тепла) и «передаче товара» (цитата нормы), хотя иск был о
возврате дома. В другом акте упоминание присоединения компании не делало
спор о субсидиарной ответственности налоговым спором.

Теперь shortlist охватывает разные формулировки и до шести PDF (не более трёх
загрузок одновременно). Локальный ранг учитывает долю словесных признаков в
акте, их совместное присутствие в коротком контексте и предмет в начале акта.
Непрочитанные PDF стоят внизу, низкие ранги сопровождаются явным сообщением.
Алгоритм не содержит запрета на банкротство или другую категорию: контрольный
запрос о субсидиарной ответственности в банкротстве получает высокий ранг.

Оба присланных пользователем PDF были пропущены через полный локальный путь
загрузки, извлечения и ранжирования: А59-7581/2023 и А49-4711/2024 получили
по **1 из 5** и корректный источник документа. Представительные положительные
контрольные тексты по поставке и налоговой реорганизации получают **4 из 5**.
Тесты проверяют также, что подходящий документ из другой поисковой
формулировки попадает в shortlist и оказывается выше ложного совпадения.

Локальный ранг остаётся **предварительным текстовым ранжированием**: синонимы,
роли сторон, отрицания и цитаты могут быть поняты неверно. После явного
разрешения пользователя добавлен отдельный модельный этап: Yandex получает
описание и максимум пять коротких фрагментов каждого проверенного PDF,
оценивает сходство фактов и правового вопроса, указывает ID фрагмента.
Запрос API `semantic_reranking=true` и видимая галочка в интерфейсе включают
передачу; по умолчанию она выключена. При ошибке модели показывается локальный
ранг и предупреждение. Пользовательские оценки хранятся только в браузере и
не меняют ранги автоматически.

**72 теста пройдены, 1 live-тест пропущен**; JavaScript проходит синтаксическую
проверку. Повторный
интеграционный smoke через текущую VPN-сеть: две попытки Parser API за общий
лимит 45 с, обе завершились тайм-аутом до HTTP-ответа, PDF не получен.
Качество живой выдачи и улучшение позиции действительно релевантного дела
через Parser API этим запуском не подтверждены.

Живой вызов нового этапа Yandex завершился HTTP 403. Контрольный вызов уже
существовавшего планировщика с теми же настройками также получил HTTP 403:
текущий API-ключ или доступ к папке Yandex надо проверить в личном кабинете.
Ключи не выводились и не менялись. Поэтому работоспособность модельного
ранжирования подтверждена контрактными тестами с подставным HTTP-ответом, но
не реальным ответом Yandex.
