# Инструкция по подключению и тестированию поиска судебных дел

## Цель тестирования

Проверить, помогает ли сервис находить судебные дела для реальной юридической задачи, а также собрать конкретные примеры для улучшения поиска, ранжирования и понимания пользовательского запроса.

### Повторный тест после обратной связи 29 сентября

Выберите **расширенный режим** и включите разрешение на смысловую проверку
GigaChat. Без этого разрешения система покажет предварительных кандидатов,
но не подтвердит юридическое сходство. Для расширенного режима сервер должен
разрешать две страницы на формулировку (`SEARCH_MAX_PAGES_PER_QUERY=2`).

Сначала оцените предмет спора, объект сделки и последовательность событий
в обязательных условиях плана. После поиска проверьте группу подтверждённых
по фрагментам совпадений, затем раскройте остальные группы и причины.
Проверьте, что ИФНС в банкротстве, покупка товаров вместо компании,
косвенное упоминание дивидендов и акт об отложении не попадают в подтверждённую
подборку. «Не виден во фрагментах» означает недостаток доказательств для
подтверждения, а «показано несоответствие» должно иметь точную цитату.

Сохраните новые оценки кнопкой «Скачать оценки»: JSON версии 2 хранит каждый
запуск один раз в `runs`, а оценки ссылаются на него через `run_id`. Внутри
`result_snapshot` доступны кандидаты, карточки, число прочитанных PDF,
страницы каждого запроса, ошибки и статусы — эти данные нужны для следующего
разбора. Старые оценки сохраняются при переходе на новый формат.

Оценивайте не только совпадение слов. Главный вопрос:

> Если бы я искал судебную практику для решения этой юридической задачи, помогли бы мне найденные дела и ответ системы?

## 1. Как подключиться

### Если вам выдали ссылку на тестовый стенд

1. Откройте полученную ссылку в браузере.
2. Если источник недоступен, сравните диагностику HTTPS с VPN и без него. VPN может влиять на доступность; это проверяется измерением, а не считается универсальной причиной.
3. Убедитесь, что в верхней части страницы указано, что GigaChat и источник судебных актов настроены.
4. Введите описание правовой ситуации и нажмите **«Найти похожие дела»**.
5. Дождитесь окончания поиска. План ограничен 45 секундами, последующий поиск — 120 секундами; неполная выдача отмечается отдельно.
6. Если страница не открывается, статус сообщает об ошибке или поиск не завершается, сначала запустите диагностику из README. Если ошибка сохраняется, зафиксируйте адрес страницы, время, текст ошибки и по возможности приложите снимок экрана.

Адрес стенда, логин и пароль команда проекта передаёт отдельно.

Не пересылайте данные для доступа и не вставляйте в запросы персональные данные или конфиденциальные материалы без отдельного согласования.

### Локальный запуск с GigaChat

1. Создайте в корне проекта файл `.env` на основе `.env.example`.
2. При сетевой ошибке выполните диагностику HTTPS из README.
3. Заполните как минимум:

   ```dotenv
   COURT_PROVIDER=parser_api
   PARSER_API_KEY=ваш_ключ
   LLM_PROVIDER=gigachat
   GIGACHAT_AUTH_KEY=ваш_ключ_авторизации_GigaChat_API
   GIGACHAT_SCOPE=GIGACHAT_API_PERS
   GIGACHAT_PLAN_MODEL=GigaChat-2
   GIGACHAT_RELEVANCE_MODEL=GigaChat-2-Pro
   ```

4. Установите зависимости и запустите сервер:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

5. Откройте `http://127.0.0.1:8000/demo`.

При запуске сервис читает `.env` и выбирает провайдер `gigachat`. На старте он не делает вызов модели; при поиске отправляет описание для формирования плана. Локально устанавливать LLM не требуется. Для корпоративного доступа уточните значение `GIGACHAT_SCOPE` в личном кабинете.

Ключи храните только в `.env` или переменных окружения. Не отправляйте файл `.env` и не добавляйте его в Git.

## 2. Как составить тестовый запрос

Формулируйте запрос так, как его сформулировал бы юрист в реальной работе.

Не подстраивайте лексику под систему и не добавляйте искусственно большое количество ключевых слов.

По возможности проверьте разные виды запросов:

- конкретная правовая ситуация;
- тип или категория спора;
- фактические обстоятельства;
- применённые нормы права;
- требуемый исход;
- суд, период или инстанция;
- сочетание нескольких условий;
- ситуация, описанная без точных юридических терминов.

Пример:

> Найти дела о процессуальном правопреемстве после реорганизации ответчика, где суд удовлетворил заявление о замене стороны.

Сохраните точный текст запроса и все выбранные фильтры.

Если вы переформулировали запрос, считайте каждую формулировку отдельным тестом.

## 3. Что проверить в понимании запроса

На первом этапе GigaChat анализирует описание пользователя и формирует поисковый план.

В карточке каждого результата теперь виден список **всех** обязательных признаков из плана.
Для проверенного PDF рядом с каждым признаком указано, найдены ли его слова и формы
в близком контексте; найденные слова выделены в точной цитате из документа.
Если PDF не удалось прочитать, это показано отдельно. Сверяйте цитату с самим актом:
такая локальная проверка может пропустить синонимы и не доказывает, что юридический
факт действительно имел место. При включённой галочке GigaChat получает список
обязательных признаков и короткие фрагменты PDF. В том же дополнительном вызове
он оценивает и сходство дела в целом, и каждый признак отдельно. Положительная
оценка привязана к конкретному фрагменту, а дословная цитата подсвечена.
«Не виден во фрагментах» не означает,
что признака нет в полном судебном акте; проверяйте исходный PDF.

Перед оценкой найденных дел посмотрите, правильно ли система поняла исходную задачу.

Отмечайте:

- правильно ли определена правовая ситуация;
- сохранены ли все существенные факты;
- сохранены ли ограничения пользователя;
- сохранён ли требуемый исход;
- не заменено ли юридическое понятие похожим, но иным;
- не добавлены ли обстоятельства, которых не было в запросе;
- полезны ли сформированные поисковые формулировки;
- корректно ли выделены обязательные признаки;
- корректно ли выделены исключающие признаки;
- не потеряна ли важная часть исходного запроса.

Особенно важно фиксировать ситуации, когда система:

- неправильно определила правовую ситуацию;
- потеряла одно из ключевых условий;
- добавила условие, которого не было в запросе;
- смешала разные юридические понятия;
- слишком сильно упростила запрос;
- сформировала поисковые запросы, которые уводят поиск в другую тематику.

Это помогает отдельно понять, связана ли проблема с интерпретацией запроса или уже с поиском судебных дел.

## 4. Как оценивать поисковую выдачу

В экономном режиме сервис читает до двух PDF, в расширенном — до шести. Большое число найденных кандидатов не означает, что все их PDF прочитаны. Если включено согласие на GigaChat, карточки показывают «Сходство ситуации»; иначе — «Текстовый ранг». Оба значения служат для сортировки и не заменяют вашу юридическую оценку дела. Сравните их с собственной оценкой и укажите причины расхождений.

Для каждого результата поставьте одну оценку:

- **Релевантно** — совпадают основной юридический смысл и ключевые условия.
- **Частично релевантно** — дело связано с темой, но одно или несколько важных условий не выполнены.
- **Нерелевантно** — совпадают отдельные слова или общая тема, но юридическая ситуация другая.
- **Невозможно проверить** — недостаточно текста, не открывается документ или отсутствуют необходимые реквизиты.

Для частично релевантного, нерелевантного или непроверяемого результата обязательно укажите причину.

Например:

- реорганизация упоминается, но правопреемство судом не рассматривалось;
- речь идёт об уступке требования, а не о процессуальном правопреемстве;
- обстоятельства совпадают, но исход противоположный;
- не совпадают суд, период или инстанция;
- событие упомянуто только как фон и не является предметом спора;
- совпадают ключевые слова, но фактическая ситуация другая;
- нужная норма приведена, но применена к другому вопросу;
- PDF или ссылка на источник недоступны.

## 5. Что считать хорошим результатом

Отмечайте не только ошибки, но и сильные примеры.

Они нужны для того, чтобы при дальнейших изменениях не ухудшить уже работающие элементы системы.

Хорошими признаками считаются:

- совпали правовая ситуация и существенные факты;
- совпали предмет требования и исход;
- найден нужный вид правоотношений;
- корректно учтены суд, период и инстанция;
- дело найдено несмотря на другую терминологию;
- наиболее полезное дело находится среди первых результатов;
- дело соответствует не только по словам, но и по юридическому смыслу;
- система правильно отделила основную правовую ситуацию от второстепенных упоминаний;
- ссылки и реквизиты позволяют быстро проверить результат.

Особенно ценны случаи, когда система нашла подходящее дело, хотя в нём использована другая формулировка или другая юридическая терминология.

## 6. Как проверять юридический смысл

Не оценивайте результат только по совпадению слов.

Например, наличие в судебном акте слова «реорганизация» ещё не означает, что дело посвящено последствиям реорганизации.

При оценке дела желательно определить:

- какое правоотношение рассматривается;
- какие фактические обстоятельства являются существенными;
- что произошло между сторонами;
- какой вопрос решал суд;
- какие требования были заявлены;
- какие нормы права применялись;
- какой вывод сделал суд;
- какой был итог рассмотрения;
- насколько всё это соответствует исходному поисковому запросу.

Главный критерий — совпадение юридического смысла и существенных обстоятельств.

## 7. Как проверить ранжирование

Даже если подходящее дело найдено, проблема может находиться в порядке результатов.

Например:

1. нерелевантное дело;
2. частично релевантное;
3. нерелевантное;
4. полностью релевантное.

В такой ситуации система смогла найти нужное дело, но неправильно определила его место в выдаче.

Отмечайте:

- позицию наиболее релевантного результата;
- нерелевантные дела в первых строках;
- частично релевантные дела выше полностью релевантных;
- формально похожее дело выше дела с близкими фактическими обстоятельствами;
- однообразные результаты;
- дубли одного дела;
- несколько актов одного дела, показанных как отдельные результаты;
- ситуацию, когда лучший результат находится слишком низко.

## 8. Как проверять пропущенные дела

Если вам известно очевидно подходящее дело, которого нет в выдаче, обязательно зафиксируйте это.

Укажите:

- номер дела;
- почему оно соответствует запросу;
- какие обстоятельства делают его релевантным;
- примерно на какой позиции вы ожидали его увидеть.

Пропущенные релевантные дела так же важны, как ошибочно найденные.

Особенно ценны случаи, когда дело явно соответствует запросу, но система его не нашла из-за другой терминологии или формулировки правовой ситуации.

## 9. Как понять, где возникла проблема

Во время тестирования желательно определить, на каком этапе возникла ошибка.

### Проблема понимания запроса

GigaChat неправильно интерпретировал исходную задачу.

Например:

- потерял важное условие;
- неверно определил тип спора;
- добавил отсутствующее обстоятельство;
- сформировал неподходящие поисковые формулировки.

### Проблема поиска

Запрос понят правильно, но подходящие дела не найдены.

Например:

- известное релевантное дело отсутствует;
- найдено слишком мало подходящих дел;
- поиск слишком зависит от точного совпадения формулировок.

### Проблема ранжирования

Подходящее дело найдено, но находится слишком низко.

Например:

- нерелевантные результаты стоят выше;
- дела с формальным совпадением терминов расположены выше дел с похожими фактическими обстоятельствами.

### Проблема данных или источника

Система нашла дело, но его невозможно нормально проверить.

Например:

- PDF недоступен;
- отсутствует текст;
- неверная ссылка;
- отсутствуют реквизиты;
- один судебный акт ошибочно отображается несколько раз.

Такое разделение особенно важно, потому что разные типы ошибок требуют разных изменений в системе.

## 10. Рекомендуемый сценарий одной проверки

1. Введите естественный запрос без адаптации под систему.
2. Сохраните запрос, фильтры, дату и время теста.
3. Проверьте, правильно ли система поняла исходную правовую ситуацию.
4. Просмотрите минимум первые пять результатов.
5. Откройте исходные документы и проверьте факты и реквизиты.
6. Присвойте каждому результату оценку.
7. Кратко объясните причину оценки.
8. Проверьте порядок результатов.
9. Проверьте наличие известных вам релевантных дел.
10. При необходимости измените формулировку запроса и запустите новый тест.
11. Запишите сильные стороны и повторяющиеся ошибки.
12. По возможности укажите, к какому типу относится проблема: понимание запроса, поиск, ранжирование или данные.

## 12. Особенно ценные примеры

В первую очередь передавайте команде случаи, когда:

- два дела похожи по тексту, но юридически различаются;
- термин присутствует, но относится к другой правовой ситуации;
- событие только упоминается и не рассматривается судом;
- тип спора совпадает, а существенные обстоятельства отличаются;
- совпадает всё, кроме исхода;
- неверно определена роль первой, апелляционной или кассационной инстанции;
- подходящее дело находится слишком низко;
- подходящее дело отсутствует;
- хорошее дело найдено по другой терминологии;
- система неправильно поняла запрос, но поиск случайно дал полезный результат;
- система правильно поняла запрос, но выдача оказалась слабой;
- релевантное дело находится ниже результата, который совпадает только по ключевым словам;
- один и тот же судебный акт или дело отображаются несколько раз;
- система неправильно связала несколько судебных актов одного дела;
- после небольшой переформулировки запроса результаты сильно изменились;
- естественный запрос работает хуже, чем запрос с точными юридическими терминами.

## 13. Важные ограничения

Результаты поиска и пояснения системы являются инструментом для первичного отбора судебной практики, а не готовым юридическим заключением.

Перед использованием результата в работе необходимо проверить:

- номер дела;
- стороны;
- суд;
- дату судебного акта;
- инстанцию;
- фактические обстоятельства;
- вывод суда;
- применённые нормы;
- актуальность правового регулирования.

Проверяйте информацию по первоисточнику.

Не включайте в отчёт:

- пароли;
- API-ключи;
- содержимое `.env`;
- персональные данные;
- конфиденциальные документы.

Для воспроизведения технической ошибки обычно достаточно указать:

- запрос;
- выбранные фильтры;
- дату и время;
- позицию результата;
- текст ошибки;
- снимок экрана.

## Обновление после аудита 25 сентября 2026

Под каждой формулировкой, обязательным признаком, проверенным судебным актом и
делом есть оценка 1–5 и комментарий. Кнопка «Скачать оценки» выгружает JSON с
описанием, планом, идентификаторами и версией. Оценки сохраняются локально в
этом браузере; сами на сервер не отправляются. Если браузер запрещает локальное
хранилище, выгрузите оценки до закрытия страницы.

Не считайте «слова всех признаков найдены» юридическим подтверждением. Для
каждого признака видна цитата, которая может требовать проверки контекста.
Непроверенный PDF, отсутствие слов и явное отсутствие факта — разные ситуации.
Если источник недоступен, пустую выдачу не надо оценивать как качество поиска.

При повторном тестировании используйте все три исходных сценария коллег
(передача имущества государству, покупка/присоединение с займом, аренда с
выкупом), плюс положительный запрос о банкротстве и запрос другой категории.
Не фиксируйте случайный порядок выдачи внешнего сервиса как эталон.
